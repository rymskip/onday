# feat(mcp): start a new session's browser from an earlier session's profile

- **Date:** 2026-10-28 15:42
- **Commit:** c59bd2b
- **Area:** MCP server

## Problem

Every new MCP session started its browser on an empty profile. Extensions installed in an earlier session, their own storage and sign-in, and site logins all had to be set up again. The only way to keep them was to reuse the earlier session itself, which takes it over rather than leaving it as it was.

## Cause

A session's profile lives in its own directory, `<session>/profile-<engine>/`, and nothing could start one from another session's.

## Introduced

None. Sessions have always started from an empty profile.

## Fix

`--profile-from <session>` (`ONDAY_PROFILE_FROM`) copies the earlier session's profile for the engine being launched into the new session before the first launch. The copy is the whole profile, so extensions keep their files, storage and service workers, and cookies, saved logins, local storage and IndexedDB carry over. Chromium's `Singleton*` links, version marker and `DevToolsActivePort`, and Firefox's lock files, stay behind. The copy is built under `.partial` and renamed into place once complete. The earlier session's lock is held while copying, so a session still open in another process is refused. A session that already has a profile, or names itself, is refused too, and a relaunch in the same session keeps the profile its first launch made. `browser_status` reports the session a profile started from. The option conflicts with `--isolated`.

## Verified

- `cargo test -p onday_mcp`: 10 tests pass. They cover the whole profile copied with nested files and links but without its claims, the earlier session left unchanged, refusals for a held session, a missing engine profile, a missing session, an existing profile and a session naming itself, and an interrupted copy replaced.
- `cargo test -p onday_mcp a_copied_chromium_profile -- --ignored`: Chrome 156 stored a persistent cookie, local storage and an IndexedDB record on a local page, onday copied that profile, and a second Chrome on the copy read all three back.
- The built `onday_mcp` over stdio: session `earlier` set a cookie and local storage; `later` with `--profile-from earlier` reported the source in `browser_status`, logged the copy, and read `session=kept` from both; starting `later` again with the option was refused because it now had a profile.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` is clean.
- Extensions themselves were not exercised: branded Chrome ignores `--load-extension` and no Chrome for Testing build is installed here, so the check covers the stores extensions keep their data in, not an installed extension.
