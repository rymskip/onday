# fix(locator): drag in Playwright's steps, one move onto the target

- **Date:** 2026-10-18 17:04
- **Commit:** 09929cc
- **Area:** Locator

## Problem

An application's e2e drag of a sidebar card onto an empty calendar slot ended without a drop: the page received `dragstart` and then only `dragend` on the target slot, so nothing was rescheduled.

## Cause

`drag_to` pressed the button, paused 50 ms, then glided to the target in ten 16 ms steps and released, all in one input batch. The glide crossed calendar cards that refuse the drop, and the button came up on the slot straight after crossing them; the browser ended the drag there without a `drop`. Playwright does none of this: it moves to the source, presses, aims the target again, makes one move onto it, and releases, each its own input call.

## Introduced

e8050d3 (2026-09-12), `feat(onday): WebDriver BiDi browser automation and an MCP server`, which drove a drag as one batch with the pause and the stepped glide.

## Fix

`drag_to` follows Playwright's sequence: move onto the source, press, aim the target once the button is down (pressing can move it), one move onto the target, release, each a separate input call. The glide, its step constant and the pause are gone, along with the `Pause` pointer action and the move `duration` nothing sets any more.

## Verified

The application's two failing drag tests, run against this checkout, both passed; the first now logs a trusted `drop` on the target slot where it logged only `dragend` before. `cargo fmt --all --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo test --workspace --all-features`, and `cargo test -p onday --test browser chromium_over -- --ignored`, 2 passed.
