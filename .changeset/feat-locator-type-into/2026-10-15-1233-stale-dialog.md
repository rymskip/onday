# fix(page): handle a dialog's opening and closing in order, and drop it from the record when answered

- **Date:** 2026-10-15 12:33
- **Commit:** 12e8993
- **Area:** Page

## Problem

Through the MCP, navigating away from a form with unsaved edits reported a `beforeunload` dialog under "Modal state", and every later tool was told to answer it first. `browser_handle_dialog` then failed with `no such alert — No dialog is showing`, and the page stayed unusable until the session was restarted.

## Cause

The page records a dialog on `browsingContext.userPromptOpened` and clears it on `userPromptClosed` or a successful answer. The two events ran on separate tasks, so nothing ordered them. Logged over BiDi, chromedriver answers a `beforeunload` itself and sends its closing 14 ms after its opening, close enough for the closing to be handled first and the opening to record a dialog that was already gone. Answering it then failed, and a failed answer left the record in place.

## Introduced

e8050d3 (2026-09-12), "feat(onday): WebDriver BiDi browser automation and an MCP server", which subscribed to the two events on separate streams and cleared the record only after a successful answer.

## Fix

Both prompt events are handled on one ordered raw stream, as network events already are. Answering a dialog takes it off the record before the answer is sent, as Playwright's dialog manager does, so a failed answer leaves nothing to wait on.

## Verified

`cargo fmt --all`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo test --workspace --all-features` and `cargo test -p onday --test browser -- --ignored` (6 passed). The scenario registers a `beforeunload` handler before navigating to the second page and checks no dialog is on record after it lands. The reversed handling was not reproduced: in the logged runs the closing was handled after the opening.
