# fix(launch): remove the log chromedriver's BiDi tab renders every message into

- **Date:** 2026-10-12 15:04
- **Commit:** 02c9830
- **Area:** Launch

## Problem

On Chromium over BiDi, a page that issued many requests held every command up. With 1,200 requests the page itself finished loading in 1.3 s, the request events took 21 to 27 s to arrive, and a command asked one second in was answered after 20.6 s. Afterwards each command still took 200 to 330 ms.

## Cause

chromedriver implements BiDi with a script, the BiDi-CDP mapper, running in a tab of the browser. Its `log` function writes every BiDi message the tab sends into a `#logs` element on the tab's own page: pretty-printed JSON in a new `div`, the oldest removed past 400. A request event is about 5.7 KB of that text, and the tab spends about 9 ms laying each one out, in lumps of over a second. The tab's renderer was at 100% of a core for the whole backlog (27 s of CPU in a 28 s flood) while the page under test used 2.3 s. Command replies leave through the same tab, so they wait behind the events.

The raw debugger events the tab receives do not go through that function. With no request events subscribed it received all 4,200 of them for 600 requests and answered commands in 3 to 5 ms.

The delay scales with the number of events, not their square: 5 s at 300 requests, 10 s at 600, 21 s at 1,200, 37 s at 2,400. Every chromedriver from 153.0.8010.52 to 157.0.8096.0 carries the same function.

## Introduced

e8050d3 (2026-09-12), "feat(onday): WebDriver BiDi browser automation and an MCP server", which subscribes every BiDi session to the request events. The log itself is chromedriver's.

## Fix

A Chromium session over BiDi removes the `#logs` element from the mapper tab as it starts, through the driver's debugger passthrough. The mapper looks the element up before each write and skips the write when it is missing. A driver that lists no such tab is left alone, with a warning.

`tests/flood.rs` serves a page that imports 1,200 modules and fails when a command asked while they load takes over five seconds, or when any request is missing or unsettled afterwards.

## Verified

- A copy of chromedriver 155.0.8059.39 with the element's id changed by one letter, and nothing else: the 1,200 requests settled in 2.2 s, the tab used 2.0 s of CPU, commands took about 2 ms.
- `cargo test -p onday --test flood -- --ignored --test-threads=1`: Chromium passed with the slowest command at 1.19 s and all 1,202 requests settled 2.4 s in; Firefox passed at 1.39 s and 3.2 s.
- The same test with the removal switched off failed: "a command asked 1.1 s into the flood had no answer in 5s".
- `cargo test -p onday --test browser -- --ignored --test-threads=1`: the four Chromium tests and Firefox over Classic passed. Firefox over BiDi failed once at session creation, before any onday code ran, with Firefox answering "The connection was denied by the user". It passed in eight runs on its own and in a second run of the whole file.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` exited 0.
