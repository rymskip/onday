# ci(github): publish both crates to crates.io on a version tag

- **Date:** 2026-11-19 19:00
- **Commit:** e9b766e
- **Area:** CI

## Problem

A release reached crates.io only by hand. Tagging a version did nothing, so nothing tied a
published crate to a tree that had passed the checks.

## Cause

The CI ran only on pushes to `main` and on pull requests, and had no publish step.

## Introduced

none

## Fix

A tag `v*` also runs the workflow. Its `publish` job waits for `check` and `browsers`, confirms
the tag is `v` followed by the workspace version, and runs `cargo publish --workspace --locked`,
which publishes onday before onday_mcp. The registry token comes from crates.io trusted
publishing through `rust-lang/crates-io-auth-action`, pinned to its v1.0.6 commit: the job's
OIDC token is exchanged for a short-lived token the action revokes when the job ends, so no
secret is stored. The job runs in the `release` environment with `id-token: write`.

Trusted publishing works only for a crate already on crates.io, as both are, and each crate must
name this repository and `ci.yml` in its trusted publishing settings on crates.io before a tag
can publish it.

## Verified

The workflow parses as YAML, with the `v*` tag trigger and `publish` needing both check jobs. Its
version step, run locally, passed for `v0.4.1` and failed for `v0.4.2` with `tag v0.4.2 does not
name the workspace version 0.4.1`. `cargo publish --workspace --locked --dry-run` packaged and
verified onday and then onday_mcp and stopped before uploading. The job has not run on GitHub.
